# Session status detection

Each session shows a colored dot driven automatically by Claude Code hooks — no terminal scraping.

## Color → meaning

| State | Color | Trigger |
|---|---|---|
| Idle | gray | a freshly created session, or `SessionStart` — started, but no work in flight yet |
| Working | yellow (spinning) | `UserPromptSubmit`, `PreToolUse` (and any non-push `PostToolUse`) |
| Needs input | green (glowing) | **blocking asks only**: `PermissionRequest`, a `Notification` whose message names a permission ("Claude needs your permission to use X"), and `PreToolUse` for an **ask tool** (see below). The generic idle `Notification` ("Claude is waiting for your input") follows *every* unattended turn — including ones merely ending with a prose question, which agents do constantly — so it maps to null and leaves the dot alone |
| Completed | green | `Stop`, or the PTY exits |
| Background agents | green (spinning) | the **main** conversation has stopped (the chat is free to take a message) but background work — subagents, or `/fork` conversations — is still running — see [A session completes on its last agent](#finish-notification). State id `bg-agents` |
| Committed / pushed | purple | a successful per-session **Commit changes**, or a `PostToolUse` whose Bash command matches `git push` |
| Interrupted | red | the agent was stopped while actively **working**: an ESC/Ctrl+C the CLI's hook stream then confirms cut the turn short, archiving a working session, or reopening one that was working when the app closed (see [Interrupting a turn](#interrupting-a-turn) and [Persistence](#persistence-across-restarts)) |

A just-created session stays gray (idle) until the user submits the first prompt; yellow ("working") is reserved for an agent actively responding. Because "working" is the only ongoing state, its dot also **animates**: it turns into a ring spinner (a faint ring with one bright rotating segment) so an in-progress session is distinguishable from a paused one at a glance, not just by hue. A solid dot can't show rotation, so the gap in the ring is what makes the motion visible. It is intentionally **not** gated behind `prefers-reduced-motion` — it's the only liveness cue, and Windows reports "reduce" whenever the OS animation setting is off, which would silently hide it. (See `.dot.working` in `src/styles/sessions.css`.)

`bg-agents` is the **same spinner in green**: hue answers "can I type here?" (green = yes, the chat has settled), motion answers "is anything still running?" (spinning = yes, background agents). It is not `completed` — the run isn't over, so no chime, no celebration, and a restart collapses it to `interrupted` exactly like `working`; and it is not `working`, because nothing is holding the chat.

"Needs input" and "Completed" share one green signal — both mean the session wants the user's attention; the glow on "Needs input" keeps an active prompt slightly more eye-catching. The two remain distinct states (and tooltips) in code.

**Ask tools** (`isAskTool` in `ask-lib.js` — currently just `AskUserQuestion`). Claude *asking the user a multiple-choice question* is a tool call, not a notification: Claude Code fires no `Notification` for it, only an ordinary `PreToolUse`. Mapped like any other tool that would leave the session **yellow with a question on screen and nothing saying so** — and, worse, leave the phone (which renders the session as a chat and never sees the terminal) never knowing to ask it at all. So a `PreToolUse` naming an ask tool means `needs-input`; its `PostToolUse` — the answer landing — puts it back to `working` like any other tool. That same payload is where the question itself is read from (its `tool_input` carries every question and option), because the painted box cannot be read back; see [remote-access.md](remote-access.md).

## The dot on mobile

The phone renders the **same** dot from the same states, because the two halves of the product must not disagree about what a session is doing. `mobile/src/components/StateDot.tsx` is the single implementation (used by both the sessions list and the chat header) and ports the desktop CSS to RN `Animated`: the yellow ring spinner (700ms linear loop, reused in green for `bg-agents`), the green `needs-input` glow, and the working → completed pop + expanding ring (500/600ms) — same colors, same durations, same one transition that triggers the celebration. Colors come only from `stateColor` in `mobile/src/theme.ts` (the desktop's GitHub-dark hues); a screen must never spell its own state palette out in hex, which is how the sessions list once drifted to One Dark, painted `pushed` green instead of purple, and left `needs-input` gray because it keyed off a `waiting` state that no code ever produces. The dot sits in a fixed-width slot on both screens, since the working ring is wider than the resting dot and would otherwise nudge the row's text sideways whenever a session started or stopped.

The chime is desktop-only: the phone plays the visual celebration but no sound.

## Finish notification

The moment a session goes from **working** (yellow) to **completed** (green) — the only transition that means "the thing you were waiting on just finished" — the sidebar plays a one-shot attention cue: the row flashes green and its dot bounces with an expanding ring (`.just-finished` in `src/styles/sessions.css`), and a short chime plays. The result is usually off-screen (a background session, or the user looking elsewhere), so this pulls the eye back. `setState()` (renderer `sessions.js`) detects the transition via the pure `isCompletionTransition(prev, next)` and calls `celebrateFinish()`, which (re)applies the animation classes and calls `playNotification()`.

Only **working → completed** (or **bg-agents → completed**, the last background agent landing) fires it — not `needs-input` (also green) and not any already-settled state moving to `completed` (e.g. a restored session). The trigger is the pure, unit-tested `isCompletionTransition` in `src/renderer/shared/notify.js` (`test/notify.test.mjs`).

**A session completes on its last agent, not its first.** `deriveStatus(payload, tracking, { originId, now })` (pure, in `hook-events.js`) layers this over `eventToState`. Two different things can outlive the main agent's turn, and **both** hold the session yellow:

- **Subagents** — spawned via the `Task` tool (named `Agent` on newer CLIs; both count), plus Codex's own `SubagentStart`. They run *inside* the session and announce themselves with `agent_id`, so they're **counted**: spawns against subagent stops. Claude Code fires the main `Stop` while they keep working, then one subagent stop per subagent as each finishes.
- **Agents nobody announced** — counting spawns only works for work the *main thread* asked for. A `/fork` is a **slash command**: no `Task`/`Agent` `PreToolUse` ever fires, so the spawn count stays 0, and the fork then speaks only through events carrying its `agent_id` — which the subagent-context branch dropped wholesale. Net effect: a session with a fork hard at work sat **flat green** (`completed`). So an `agent_id` we haven't seen before is itself the evidence that an agent is alive: it's registered in `agents: [{id, at}]` (stamped, so one that dies without a stop ages out like a stale origin). A first sighting **claims an open spawn slot** if there is one, so a `Task` subagent counted at `PreToolUse` isn't counted twice. In-flight background work is `subagents + agents.length`.
- **Forked conversations** (`/fork`) — *not* subagents. The CLI runs each fork as a **separate conversation with its own `session_id`** and no `agent_id`, so once `normalizeHookPayload` maps it back onto our session a fork's `Stop` was indistinguishable from the main agent finishing. That's why a session with forks still working went **green**: the first `Stop` from any of them settled the whole session (and rang the chime). So the tracking holds the **set of conversations currently in flight** (`active: [{id, at}]`, keyed by the CLI's own session id — `originId`, which the hook server takes from `normalizeHookPayload`) rather than one `mainStopped` boolean. Each conversation's activity adds it; each conversation's `Stop` removes **only itself**.

**Hue answers "can I type here?", motion answers "is anything still running?"** — and those are two different questions, so they're read off two different things. The dot is `working` (yellow) only while the **main** conversation itself is in flight; that's the one that blocks the chat. Everything else that can outlive it — subagents, and forks, which are their own conversations — is *background*: it can't turn the dot yellow, it only keeps it spinning. So once the main conversation has stopped: `completed` if nothing else is left, `bg-agents` (green spinner) while any fork or subagent runs on. This holds in both orderings — a fork already running when main stops, and a fork whose events only start arriving *after* main stopped (its activity un-settles a green dot into a spinning one).

The `stopped` flag is what distinguishes an empty `active` set *before* any work from one *after* the last stop; without it a stray subagent stop would settle the session. `UserPromptSubmit` resets the bookkeeping (counts, stopped ids, `stopped`) only when **nothing is in flight** *and* the prompt came from the **main origin** — a fork prompting itself is not a fresh turn for the session, and a fork clearing `stopped` is exactly what made its background work read as the main agent being busy (yellow) instead of the green spinner.

`/fork` has a second shape the hook stream can't announce: it can **replace** the conversation, so the old session id simply stops existing and never fires its `Stop`. An origin with no hook in `ORIGIN_STALE_MS` (5 min — every tool call refreshes its stamp, so only a truly abandoned one ages out) is swept from `active`; that's the escape hatch that keeps such a session from hanging yellow forever.

The hook server (`hook-server.js`) holds the per-session `{ subagents, active, stopped, stoppedIds }` tracking in an in-memory `Map` (nothing runs across a restart, so it isn't persisted) and threads it through each event with `Date.now()`; `sessions.js` calls `hookServer.clearTracking(id)` on PTY exit (which covers archive and close too — the dying PTY takes every agent with it), so a resumed session never inherits a stale count. `SubagentStop` is in the `hooksSettings()` event list for this reason. Unit-tested in `test/hook-events.test.js`. Like the working spinner, the animation is **not** gated behind `prefers-reduced-motion` — it's a functional attention cue and Windows reports "reduce" whenever OS animations are off, which would silently kill it; it's a single short pulse, not sustained motion.

Every hook payload that carries `agent_id` fired **inside a subagent's own context**, never the main thread — Claude Code sets it only there (main-thread events never have it). `deriveStatus` classifies these up front: a stop from a subagent context (`SubagentStop`, or a `Stop` carrying `agent_id` — some CLI versions mis-route a subagent's stop that way) **decrements the in-flight count** via `isSubagentStop()` — but only **once per `agent_id`**: some CLI versions fire *both* a `SubagentStop` and a mis-routed `Stop` for the same finishing subagent, and counting both would drain the count for two agents and ring the chime while another background agent still runs (tracking carries a per-turn `stoppedIds` list, reset with the rest on `UserPromptSubmit`) — and *every other* `agent_id` payload is ignored entirely — it touches neither the dot nor the bookkeeping, so a subagent's `UserPromptSubmit` can't wipe the count, its `Stop` can't fake the main agent stopping, and its tool activity can't fire the chime early. `eventToState()` keeps its own `agent_id` guard as defense in depth. The wrapping Task/Agent tool call still keeps the session `working` via its own (agent_id-less) `PreToolUse`/`PostToolUse`, so nothing is lost by ignoring the subagent's internal events.

The chime is one of four sounds the user picks in **Settings → Notification sound** (see [settings.md](settings.md#notification-sound)). The sounds are **synthesized with the Web Audio API**, not shipped as audio files — no binary asset, works offline under `file://`, matching the app's pure-CSS/synth approach. `notify.js` owns the `SOUNDS` registry (each a list of oscillator voices with a pluck/bell envelope), the persisted choice (`localStorage` `ide.notifySound`, default `chime`), and a shared lazily-created `AudioContext` (resumed on each play to survive the autoplay policy).

The same transition can also raise an OS-level desktop notification — opt-in via **Settings → Desktop notifications** (off by default, since unlike the chime it can steal window focus). See [settings.md](settings.md#general-preferences).

## How it works

`hooksSettings()` builds an inline hooks config and passes it to each session via the `claude --settings <json>` flag — so the user's global `~/.claude/settings.json` is **never modified**. (The same inline settings also carry the per-session [token meter](architecture.md#per-session-token-meter)'s `statusLine`, and `disableAgentView: true` — this app already lists sessions side by side, so Claude Code's own `claude agents` background-agent screen is turned off in every spawned session. There's no CLI flag for it; the setting and the `CLAUDE_CODE_DISABLE_AGENT_VIEW` env var are the only toggles.) Every hook is a `command` hook that `curl`s its stdin payload to a local `http` server started in `startHookServer()`. `eventToState()` maps `hook_event_name` → state; the result is pushed to the renderer keyed by `session_id`.

**Every hook URL is tagged `?ide=<our session id>`** (`hooksSettings(port, statusLineCommand, ideId)`), and `normalizeHookPayload` rewrites `payload.session_id` to that id whenever the CLI reports a different one. Claude *is* spawned with `--session-id <our uuid>`, but it does not keep it for life: **`/fork` continues the conversation in a brand-new session** with a new id and a new transcript file. Those payloads named a session the app had never heard of, so `recordSessionActivity()` dropped them at its `sessions.get()` miss — a forked chat's file edits were never tracked (and so never committable), its dot never moved, and its chat never followed the new transcript. The URL tag is the one thing the CLI cannot rewrite, so it is what keeps a fork attributed to the session that spawned it. The CLI's own current id is recorded as the session's `agentSessionId`, and it is also what `deriveStatus` uses as the payload's `originId` so a fork's `Stop` can't settle the whole session (see [Finish notification](#finish-notification)). (Ordinary subagents need none of this — a `Task`/`Agent` subagent's hooks already fire with the parent `session_id`, plus an `agent_id`.)

The same payloads feed `recordSessionActivity()`, which records each session's first prompt (`UserPromptSubmit.prompt`) and its edits — each `PostToolUse` of a file tool is kept as a replayable op (`old_string`/`new_string`/content), not just the path. That op log is what lets the per-session commit reconstruct and commit only that session's hunks. It also diffs `git status` across each non-edit tool call (`PreToolUse` → `PostToolUse`) to attribute binary creates, renames/moves, and deletes — changes no text op can express — to the session (see [Tracking filesystem changes](architecture.md#tracking-filesystem-changes)). Because the `PreToolUse` snapshot must predate the tool's writes, the hook server **awaits** `recordSessionActivity()` before answering the hook (a command hook blocks its tool until `curl` returns). See [architecture.md](architecture.md).

## Interrupting a turn

Stopping an agent mid-response turns the dot **red (interrupted)**. Claude Code emits **no dedicated hook** for an interrupt, so this is the one state a keystroke has any say in — but **the keystroke alone is never believed**, because it is only a *request*. The TUI swallows ESC/Ctrl+C for its own reasons constantly (dismissing an overlay, clearing a half-typed prompt), and a stray press against a dot that is merely stale interrupts nothing at all — so trusting the keypress by itself painted still-running sessions red.

- **ESC / Ctrl+C while working.** The `pty-input` handler (`src/main/sessions.js`) runs each keystroke through the pure `isInterruptKey(data, current)` (`hook-events.js`): a bare ESC (`\x1b`) or Ctrl+C (`\x03`) counts **only when the session is currently `working`**, and arrow/function keys arrive as multi-byte sequences (`\x1b[…`) so an exact match never catches them. A hit does **not** move the dot — it opens a *pending interrupt* (`noteInterruptKey`), and the CLI's own hook stream, the source every other state comes from, arbitrates it (`resolveInterrupt`, called by the hook server for every payload before the state is applied):
  - the turn **ends** right after (a `Stop`, i.e. derived `completed`) → the interrupt landed: red, and **no** completion chime (`interruptOutcome`);
  - **anything else** arrives — a tool call, a new prompt, a permission ask → the agent is still running, so the keystroke wasn't an interrupt and the dot stays wherever the hooks put it;
  - **nothing** arrives within `INTERRUPT_GRACE_MS` (2.5 s) → a session that went silent right after an interrupt request was interrupted. This fallback is what covers CLI versions that fire no `Stop` on an interrupt either.

  Subagent-context payloads (`agent_id`) never resolve a pending interrupt — a subagent stopping says nothing about the session's own turn. A dying PTY clears it (the exit already settles the dot). The next prompt fires `UserPromptSubmit` → `working` again.
- **Archiving an active session.** Suspending (archiving) a session kills its Claude process, so a session that was `working` can't keep running. The `suspend-session` handler reuses `persistedState()` (the same rule app-close applies) to collapse `working` (and `bg-agents`, whose background agents die with the process too) to `interrupted`; a `needs-input` session was only paused for the user, so it collapses to green (`completed`), and the settled states (`completed`/`pushed`/`idle`) pass through unchanged.

Both paths are unit-tested via the pure helpers (`isInterruptKey` / `interruptOutcome` in `test/hook-events.test.js`; `persistedState` in `test/session-persist.test.js`).

## Persistence across restarts

The dot state is saved with the session snapshot so it survives closing the app. As the hook server maps each event to a state, it also calls `sessions.setSessionState()` to record the live value on the session record (and a successful per-session commit marks it `pushed`); `serializeSession()` then writes it to the session's own file (see [Session persistence](architecture.md#session-persistence)), saved immediately on the state change. Only a session that was **actively working** when the app closed (`working` — the yellow spinner) is rewritten by `persistedState()` to **`interrupted`** (red), because that turn was cut off and the restored session's Claude process can't outlive the app. A `needs-input` session was *paused waiting for the user*, not crunching — it shows green like a finished one, so it reopens `completed` (green) rather than red; the live input prompt can't survive a restart, so the glowing needs-input cue collapses to plain settled green. The other settled states are kept verbatim: `completed` (green), `pushed` (purple), and `idle` (gray — a session created but never used). On startup `restoreSessionRow()` paints the dot from the persisted state; selecting the session resumes its Claude process, which then drives the dot live again. `persistedState()` lives in the Electron-free `session-persist.js` and is unit-tested.

Resuming a saved session fires a `SessionStart` (→ `idle`), which would otherwise reset a reopened session's dot to gray the instant the user clicks it. So the hook server **suppresses an `idle` that would downgrade an already-meaningful state**: it checks `sessions.getSessionState()` and only applies `idle` when the session has no prior state (a brand-new session is already idle, so it's unaffected). A reopened `completed`/`pushed`/`interrupted` session therefore keeps its colour until real new work (`working`/`needs-input`/…) moves it.

## Codex sessions

Codex CLI sessions (`codex:` models — see [codex.md](codex.md)) feed the **same pipeline**: their hooks are injected as `-c hooks.<Event>=…` spawn overrides posting to the same server, and their payloads are Claude-shaped. Two deltas live in `hook-events.js`: `deriveStatus` counts Codex's own **`SubagentStart`** event as a spawn signal (handled before the `agent_id` early-return so it balances its `SubagentStop` from either context), and **`normalizeHookPayload`** rewrites the Codex-invented `session_id` back to the IDE's id using the `?ide=` query param on the hook URL (recording the original as the session's `agentSessionId`, which `codex resume` needs). `hook-server.js` also strips a leading UTF-8 BOM before `JSON.parse` — Codex-on-Windows runs hook commands through PowerShell, whose stdin piping prepends one. The `PostToolUse` git-push sniff accepts an argv-array `command` too.

## Load-bearing assumptions

- **Hook event names** (`events[]` in `main.js`). If status dots never change, a CLI-version event-name mismatch is the first suspect. Unknown names are harmless — they simply never fire.
- **`curl` on PATH** to deliver hook payloads (ships with Windows 11). Codex hook commands must say `curl.exe` and quote `'@-'` (PowerShell).
- **`session_id` correlation**: guaranteed by the `?ide=` tag on every hook URL plus `normalizeHookPayload` — for Codex (which has no `--session-id`) and equally for a Claude session that has forked into a new id.
